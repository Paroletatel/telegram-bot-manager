# PhoneNumbers

## Модель данных

### PhoneNumber

Модель для хранения информации о телефонных номерах пользователей:

- `userId` (string): Идентификатор пользователя (уникальный)
- `userName` (string): Имя пользователя
- `phoneNumber` (string): Номер телефона (уникальный)
- `phoneNumberStatus` (string): Статус номера телефона (new, approved)
- `messageStatus` (string): Статус сообщения (null, forSend, sended)

## Методы сервиса

### _async checkNewMember(userId: string)_

Проверяет существование номера телефона у нового участника.

**Логика работы:**

1. Поиск записи в таблице `PhoneNumber` по указанному `userId`
2. Возвращает 'exists', если пользователь найден, или 'new', если не найден

### _async createNewMemberToRegistration(userId: string, phoneNumber: string, userName: string, tgSurname: string, tgName: string, tgUserName: string)_

Создает нового участника регистрации и связывает его с телефонным номером.

**Логика работы:**

1. Форматирует номер телефона с помощью утилиты `formatPhoneNumber`
2. Проверяет наличие формы, созданной администратором, с указанным номером телефона
3. Если форма найдена:
   - Создает запись в `PhoneNumber` со статусом 'approved' и messageStatus 'sended'
   - Обновляет форму в `Form`, устанавливая статус 'approved' и добавляя данные из Telegram
4. Если форма не найдена:
   - Создает запись в `PhoneNumber` со статусом 'new' и messageStatus null
   - Создает новую форму в `NewForm` со статусом 'created' и базовыми данными из Telegram

### _async getNewNumbersList()_

Получает список новых номеров телефонов.

**Логика работы:**

1. Получает все записи из таблицы `PhoneNumber` со статусом 'new'
2. Возвращает массив найденных записей

### _async checkNewPhones()_

Проверяет новые номера телефонов и обновляет их статус.

**Логика работы:**

1. Получает все записи из таблицы `PhoneNumber` со статусом 'new' и messageStatus null
2. Обновляет все найденные записи, устанавливая messageStatus в 'forSend'
3. Возвращает массив найденных записей (до обновления)

### _async changeNumberStatus(phoneNumber: string, status: string)_

Изменяет статус номера телефона.

**Логика работы:**

1. Форматирует номер телефона с помощью утилиты `formatPhoneNumber`
2. Обновляет запись в таблице `PhoneNumber` по указанному номеру телефона:
   - Устанавливает phoneNumberStatus в переданный статус
   - Устанавливает messageStatus в 'forSend'

### _async getNewApprovedList()_

Получает список новых одобренных номеров телефонов.

**Логика работы:**

1. Получает все записи из таблицы `PhoneNumber` со статусом 'approved' и messageStatus 'forSend'
2. Возвращает массив найденных записей

### _async setMessageStatus(userId: string)_

Изменяет статус сообщения для пользователя.

**Логика работы:**

1. Обновляет запись в таблице `PhoneNumber` по указанному `userId`
2. Устанавливает messageStatus в 'sended'

## Взаимодействие с другими модулями

Модуль `phone-numbers` взаимодействует с другими модулями системы:

1. **Модуль `forms`**: Использует модели `Form` и `NewForm` для связи номеров телефонов с формами пользователей

## Особенности реализации

1. **Статусная система**: Используется два типа статусов - статус номера телефона и статус сообщения
2. **Форматирование номеров**: Используется утилита `formatPhoneNumber` для приведения номеров к единому формату
3. **Интеграция с Telegram**: При регистрации сохраняются данные пользователя из Telegram (tgName, tgSurname, tgUserName)
4. **Автоматическое одобрение**: Если форма с указанным номером уже существует, пользователь автоматически получает статус 'approved'

# Messages

## Модель данных

`Message` - модель сообщения со следующими полями:

- `fromUserId` (string): ID отправителя сообщения
- `fromUserName` (string): Имя отправителя сообщения
- `toUserId` (string): ID получателя сообщения
- `text` (string): Текст сообщения
- `isAuto` (boolean): Флаг автоматического сообщения
- `status` (string): Статус сообщения (new, sended, read)

## Утилиты

Модуль использует вспомогательные функции для работы с часовыми поясами:

- `getDayOfTheWeek(timezone)`: Возвращает текущий день недели с учетом часового пояса
- `getCurrentHourInTimezone(timezone)`: Возвращает текущий час и минуты с учетом часового пояса

## Методы сервиса

### _async createNewMessage(fromUserId: string, toUserId: string, text: string)_

Создает новое сообщение между пользователями и автоматический ответ при необходимости.

**Логика работы:**

1. По `fromUserId` находим форму пользователя-отправителя для получения его данных
2. Создаем сообщение со следующими параметрами:
   - `fromUserId`: ID отправителя
   - `fromUserName`: Полное имя отправителя в формате "Имя Фамилия (системное имя)"
   - `toUserId`: ID получателя
   - `text`: Текст сообщения
   - `status`: "new" (новое)
   - `isAuto`: false (не автоматическое)
3. По `toUserId` находим форму пользователя-получателя
4. По `toUserId` находим настройки пользователя-получателя
5. Если у получателя настроено автоматическое сообщение (`autoMessage`):
   - Создаем автоматический ответ со статусом "new"
   - Добавляем префикс "(Это автоматическое сообщение)"
   - Устанавливаем `isAuto: true`

### _async getNewMessages()_

Получает список новых сообщений с учетом настроек доступности получателей.

**Логика работы:**

1. Находим все сообщения со статусом "new"
2. Получаем уникальный список ID получателей (`toUserId`)
3. Получаем настройки всех этих пользователей
4. Для каждого пользователя проверяем:
   - Текущий день недели с учетом часового пояса пользователя
   - Текущее время с учетом часового пояса пользователя
   - Настройки доступности пользователя:
     - Доступные дни недели (`accessDays`)
     - Флаг доступности (`availability`)
     - Время начала доступности (`accessTimeStart`)
     - Время окончания доступности (`accessTimeEnd`)
     - Флаг круглосуточной доступности (`accessAllTime`)
5. Если пользователь доступен в текущий момент (по дню недели и времени), добавляем его сообщения в результат
6. Возвращаем отфильтрованный список сообщений

### _async changeMessageStatus(status: string, messageId: number)_

Изменяет статус сообщения.

**Логика работы:**

1. Обновляет поле `status` сообщения с указанным `messageId`
2. Новый статус устанавливается из параметра `status`

### _async getNewMessagesForUser(userId: string)_

Получает список новых сообщений для конкретного пользователя.

**Логика работы:**

1. Находит все сообщения со статусом "sended", где `toUserId` соответствует переданному `userId`
2. Для каждого сообщения:
   - Получает информацию об отправителе из таблицы форм
   - Формирует объект с данными:
     - `systemName`: Системное имя отправителя
     - `id`: ID сообщения (в виде строки)
     - `fromUserId`: ID отправителя
     - `text`: Текст сообщения
3. Возвращает массив объектов с данными сообщений

### _async getMessageById(messageId: number)_

Получает сообщение по его ID.

**Логика работы:**

1. Находит сообщение в базе данных по указанному `messageId`
2. Возвращает найденное сообщение или null, если сообщение не найдено

# Forms

## Модели данных

### Form

Основная модель формы пользователя со следующими полями:

- `userId` (string): Уникальный идентификатор пользователя
- `status` (mainFormStatuses): Статус формы ('changed', 'waiting', 'approved', 'main')
- `searchAvailability` (boolean): Доступность для поиска
- `systemName` (string): Системное имя пользователя
- `surname`, `name`, `otchestvo` (string): ФИО пользователя
- `surnameV`, `nameV`, `otchestvoV` (boolean): Флаги видимости ФИО
- `birthDate` (string): Дата рождения
- `birthDateV` (boolean): Видимость даты рождения
- `tgName`, `tgSurname`, `tgUserName` (string): Данные из Telegram
- `tgNameV`, `tgSurnameV`, `tgUserNameV` (boolean): Видимость данных из Telegram
- `registrationDate` (string): Дата регистрации
- `constPhone` (string): Основной телефон
- `constPhoneV` (boolean): Видимость основного телефона
- `organizations` (OrganizationInterface[]): Список организаций
- `contacts` (ContactInterface[]): Список контактов
- `tags` (string[]): Теги
- `recommendations` (string[]): Рекомендации
- `isUserStarted` (boolean): Флаг начала работы пользователя

### NewForm

Модель для новых форм пользователей:

- Аналогична `Form`, но имеет другие возможные статусы: 'created', 'filled', 'waiting', 'rejected'
- Используется для хранения данных о новых пользователях до их одобрения

### FormPrev

Модель для хранения предыдущих версий форм:

- Структура полей аналогична `Form`, но без полей `status` и `searchAvailability`
- Используется для сохранения предыдущего состояния формы при внесении изменений

## Интерфейсы

### OrganizationInterface

Интерфейс для хранения информации об организациях:

- `orgName` (string): Название организации
- `position` (string): Должность
- `positionVis` (boolean): Видимость должности
- `inn` (string): ИНН организации
- `country`, `region`, `city` (string): Местоположение
- `website` (string): Веб-сайт
- `websiteVis` (boolean): Видимость веб-сайта

### ContactInterface

Интерфейс для хранения контактной информации:

- `type` (contactType): Тип контакта ('email', 'phone', 'constPhone')
- `value` (string): Значение контакта
- `visibility` (boolean): Видимость контакта

## Методы сервиса

### _async continueRegistration(userId: string)_

Продолжает процесс регистрации пользователя.

**Логика работы:**

1. Создает запись в таблице настроек для пользователя с параметрами:
   - `userId`: ID пользователя
   - `availability`: true (доступен)
   - `accessAllTime`: true (доступен всегда)
2. Обновляет дату регистрации в записи `NewForm` для пользователя

### _async approveNewForm(formInfo: AppFormDTO)_

Одобряет новую форму пользователя.

**Логика работы:**

1. Проверяет, существует ли уже форма для данного пользователя
2. Если форма существует, прерывает выполнение
3. Создает новую запись в таблице `Form` со статусом 'approved' и следующими параметрами:
   - Все поля из переданного объекта `formInfo`
   - `searchAvailability`: true
   - `isUserStarted`: true
   - Приведение всех полей к нужным типам данных
4. Удаляет запись из таблицы `NewForm` для данного пользователя

### _async createFormByAdmin(formInfo: AppFormDTO)_

Создает новую форму пользователя администратором.

**Логика работы:**

1. Проверяет, существует ли уже форма с таким телефоном
2. Если форма существует, прерывает выполнение
3. Генерирует временный ID пользователя
4. Создает новую запись в таблице `Form` со статусом 'main' и следующими параметрами:
   - Все поля из переданного объекта `formInfo`
   - `userId`: сгенерированный ID
   - `searchAvailability`: true
   - `isUserStarted`: false
   - Приведение всех полей к нужным типам данных

### _async rejectNewForm(formInfo: AppFormDTO)_

Отклоняет новую форму пользователя.

**Логика работы:**

1. Обновляет статус формы в таблице `NewForm` на 'rejected'

### _async getNewFormsForApproveList()_

**Логика работы:**

   - `name`: Имя

   - `constPhone`: Основной телефон
3. Возвращает массив объектов с информацией о пользователях

### _async searchUser(value: string)_

Поиск пользователей по заданному значению.

**Логика работы:**

1. Ищет пользователей в таблице `Form`, где значение совпадает с одним из полей:
   - `systemName`

   - `name`
   - `otchestvo`
   - `constPhone`
   - `tgUserName`

3. Для каждого найденного пользователя формирует объект с информацией
4. Возвращает массив найденных пользователей

3. Формирует объект с данными формы и списком чатов
4. Возвращает полученный объект

### _async deleteUser(userId: string)_

Удаляет пользователя и все связанные с ним данные.

**Логика работы:**

1. Удаляет записи из следующих таблиц:

   - `NewForm` - новая форма (если есть)
   - `FormPrev` - предыдущая версия формы (если есть)
   - `Settings` - настройки пользователя
   - `PhoneNumber` - телефонные номера пользователя
   - `Contact` - контакты пользователя
2. Удаляет связи пользователя с чатами через `chatsService.deleteUserFromAllChats`
3. Возвращает результат удаления

### _async updateForm(formInfo: AppFormDTO)_

Обновляет форму пользователя и сохраняет предыдущую версию.

**Логика работы:**

1. Находит текущую форму пользователя в таблице `Form`
2. Сохраняет текущую версию формы в таблице `FormPrev`
3. Обновляет форму в таблице `Form` с новыми данными
4. Возвращает обновленную форму

### _async getFormById(userId: string)_

## Взаимодействие с другими модулями

Модуль `forms` тесно взаимодействует с другими модулями системы:

1. **Модуль `settings`**: Используется для создания настроек пользователя при регистрации
2. **Модуль `users-chats`**: Используется для получения списка чатов пользователя и удаления пользователя из чатов
3. **Модуль `phone-numbers`**: Используется для работы с телефонными номерами пользователей
4. **Модуль `contacts`**: Используется для работы с контактами пользователей

## Особенности реализации

1. **Статусная система**: Формы имеют различные статусы в зависимости от этапа регистрации
2. **Хранение истории изменений**: Предыдущие версии форм сохраняются в отдельной таблице
3. **Разделение новых и одобренных форм**: Новые формы хранятся в отдельной таблице до момента одобрения
4. **Управление видимостью**: Для каждого поля формы есть соответствующий флаг видимости

# Settings

## Модель данных

`Settings` - модель настроек пользователя со следующими полями:

- `userId` (string): Уникальный идентификатор пользователя
- `accessDays` (string): Дни недели, в которые пользователь доступен
- `accessTimeStart` (string): Время начала доступности
- `accessTimeEnd` (string): Время окончания доступности
- `accessAllTime` (boolean): Флаг круглосуточной доступности
- `timezone` (string): Часовой пояс пользователя
- `commonMessage` (string): Общее сообщение пользователя
- `autoMessage` (string): Автоматическое сообщение пользователя
- `availability` (boolean): Флаг доступности пользователя

## Интерфейсы

### SettingsDTO

Интерфейс для передачи данных о настройках пользователя:

- `userId` (string): Идентификатор пользователя
- `accessDays` (string): Дни недели доступности
- `accessTimeStart` (string): Время начала доступности

# Итоговый анализ системы

## Общая архитектура

Система представляет собой бэкенд-приложение на NestJS, которое обеспечивает работу Telegram-бота и веб-приложения. Архитектура системы построена на модульном принципе, где каждый модуль отвечает за определенную функциональность:

1. **phone-numbers** - управление телефонными номерами пользователей
2. **messages** - обработка сообщений между пользователями
3. **forms** - управление формами пользователей (профилями)
4. **settings** - настройки пользователей
5. **users-chats** - управление связями между пользователями и чатами
6. **contacts** - управление контактами пользователей

Система использует Sequelize ORM для работы с базой данных, что позволяет абстрагироваться от конкретной СУБД. Каждый модуль содержит свои модели данных, сервисы и контроллеры, что соответствует принципам модульности NestJS.

## Взаимодействие модулей

Модули тесно взаимодействуют между собой, что позволяет реализовать сложные бизнес-процессы:

1. **forms → settings**: Модуль `forms` использует `settings` для создания настроек пользователя при регистрации.

2. **forms → users-chats**: Модуль `forms` использует `users-chats` для получения списка чатов пользователя и удаления пользователя из чатов.

3. **messages → settings**: Модуль `messages` использует `settings` для определения доступности пользователя и автоматических ответов.

4. **phone-numbers → forms**: Модуль `phone-numbers` использует модели `Form` и `NewForm` для связи номеров телефонов с формами пользователей.

5. **contacts → forms**: Модуль `contacts` использует модель `Form` для получения информации о пользователях-контактах.

6. **users-chats → Telegram API**: Модуль `users-chats` взаимодействует с API бота для проверки членства пользователей в чатах.

Такая структура взаимодействия позволяет разделить ответственность между модулями, но в то же время создает зависимости между ними, что требует внимательного управления зависимостями.

## Особенности реализации

В системе реализован ряд ключевых особенностей, которые определяют ее функциональность и архитектуру:

1. **Статусная система** - используется для отслеживания состояния форм и сообщений. Например, формы могут иметь статусы "created", "approved", "rejected", а сообщения - "new", "sended", "read".

2. **Управление доступностью** - настройки доступности пользователей по дням недели и времени с учетом часовых поясов.

3. **Часовые пояса** - учет часовых поясов пользователей для корректного определения доступности.

4. **Автоматические сообщения** - поддержка автоматических ответов на сообщения при недоступности пользователя.

5. **Хранение истории изменений** - сохранение предыдущих версий форм в модели `FormPrev`.

6. **Ролевая модель** - разделение пользователей на роли (admin/user) с синхронизацией между ботом и веб-приложением.

7. **Интеграция с Telegram** - тесная интеграция с Telegram API для работы бота и веб-приложения.

   - `*User*` - для методов, работающих с пользователями

   - `*Contact*` - для методов, работающих с контактами
   - `*Profile*` - для методов, работающих с профилями пользователей

## Анализ структуры базы данных

При анализе структуры базы данных были выявлены следующие особенности и потенциальные проблемы:

### Отсутствие явных внешних ключей (Foreign Keys)

В моделях не определены явные внешние ключи, что может привести к проблемам с целостностью данных. Например:

- В модели `Message` поля `fromUserId` и `toUserId` должны быть связаны с пользователями
- В модели `Contact` поля `userId` и `contactUserId` должны быть связаны с пользователями
- В модели `Settings` поле `userId` должно быть связано с пользователем

**Рекомендация:** Добавить явные внешние ключи с использованием декораторов Sequelize `@ForeignKey` и `@BelongsTo`.

### Нормализация базы данных

Некоторые модели не полностью соответствуют принципам нормализации:

- В модели `Form` хранятся массивы данных (tags, organizations, recommendations, contacts), которые могли бы быть вынесены в отдельные таблицы
- В модели `Settings` хранятся сложные структуры данных в поле `availability`

**Рекомендация:** Разделить сложные структуры данных на отдельные таблицы с связями для соответствия третьей нормальной форме.

### Индексация

Отсутствуют явные индексы для полей, по которым часто происходит поиск, что может снизить производительность при большом объеме данных.

**Рекомендация:** Добавить индексы для полей, по которым часто происходит поиск, например, `userId` в разных таблицах, `phoneNumber` в таблице `PhoneNumber` и т.д.

## Оптимизация организации выполнения задач

Для оптимизации общего процесса организации выполнения задач сервисами предлагаются следующие подходы:

### 1. Разделение на слои (Layered Architecture)

Текущая архитектура уже имеет некоторое разделение на слои, но его можно улучшить:

- **Слой контроллеров** - обрабатывает HTTP-запросы, валидирует входные данные и передает их в сервисы
- **Слой сервисов** - содержит бизнес-логику приложения
- **Слой репозиториев** - отвечает за работу с базой данных
- **Слой моделей** - определяет структуру данных

### 2. Выделение общих утилит и сервисов

Некоторые функции повторяются в разных модулях и могут быть вынесены в общие сервисы:

- **UserService** - централизованное управление пользователями
- **NotificationService** - отправка уведомлений
- **TelegramService** - взаимодействие с Telegram API

### 3. Внедрение паттерна CQRS

Разделение операций чтения и записи может улучшить производительность и масштабируемость:

- **Commands** - операции, изменяющие состояние системы
- **Queries** - операции чтения данных

### 4. Внедрение системы событий (Event-Driven Architecture)

Использование событий для связи между модулями вместо прямых зависимостей:

- **События пользователей**: UserCreated, UserUpdated, UserDeleted
- **События сообщений**: MessageSent, MessageRead
- **События форм**: FormCreated, FormApproved, FormRejected

### 5. Внедрение паттерна Unit of Work

Для обеспечения атомарности операций и управления транзакциями:

- Группировка связанных операций в одну транзакцию
- Откат всех изменений в случае ошибки

Эти подходы позволят улучшить модульность, тестируемость и масштабируемость системы, а также упростить разработку и поддержку кода.
